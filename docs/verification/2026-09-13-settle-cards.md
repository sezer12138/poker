# 结算弹窗亮牌验证报告（最佳五张 · 中文牌型 · 剩余筹码，两端）

状态：功能与测试完成，全量测试与端到端冒烟通过。
本报告只记录真实跑过的命令与输出，没跑过的一律写进「未验证项」——
**两端的界面渲染都只做过逻辑层与静态检查，没有人工点过，也没有真机截图**。

## 一、改了什么

用户在结算弹窗上追加要求：除了胜负与净输赢，还要显示**每个人的牌的组合与对应的牌型名**
（高牌、同花等），以及**剩余虚拟筹码**。

| 需求 | 实现 | 位置 |
|---|---|---|
| 亮出牌的组合 | 结算窗口期内服务端算出「最佳五张」，随 `settle.changes[].cards` 下发 | `apps/server/src/rooms/showdown.ts`（新）、`apps/server/src/rooms/roomview.ts` |
| 牌型名 | 服务端给 9 个稳定类别码，中文名由各端按自己的规则页口径映射 | `apps/server/src/rooms/showdown.ts`、web `table.js` 的 `typeNameOf`、小程序 `utils/settle.js` 的 `TYPE_NAMES` |
| 剩余筹码 | 读视图里已有的 `hand.players[].stack`，服务端零改动 | web `table.js` 行模型、小程序 `utils/settle.js` |
| 两端渲染 | 弹窗每行拆成两行：金额在上，牌面 + 牌型 + 剩余筹码在下 | web `table.js`/`styles.css`、小程序 `table.wxml`/`table.wxss` |

### 亮牌口径（产品确认：赢家总是亮、弃牌者不亮）

- **摊牌**（公共牌发满五张且不止一人未弃牌）：每位未弃牌者都亮「最佳五张 + 牌型」。
- **弃牌结束**（唯一未弃牌者收池）：只亮唯一赢家。底牌不足五张时直接亮底牌、`category` 为 `null`
  （翻牌前结束就是两张底牌、没有牌型）；公共牌够五张时照常算最佳五张与牌型。
- **弃牌者永远不亮**，`changes` 里干脆不带这两个键——客户端据「有没有 `cards`」显示「未摊牌」，
  而不是靠一个 null 占位去猜。
- 这条口径与引擎视图一致（摊牌才互亮底牌），也不与「历史弃牌只在整场结束后公开」的核验规则冲突。

引擎（`packages/poker-engine`）**冻结未改动**，只调用它已导出的 `evaluate`/`compare`。
「最佳五张」与「牌型枚举」引擎没有，由 `showdown.ts` 自己补齐。

## 三、真起服务端跑出来的亮牌数据

单元测试证明不了「字段真的从 HTTP 响应里出来」。为此临时写了一个探针
（`apps/server/probe.tmp.ts`，真起服务端、真打两手持牌，用完已删除，`git status` 确认无残留），
把两端的 `settle.changes` 原样打出来。

**摊牌（双方过牌到河牌）：**

```
公共牌: 28,32,35,13,42
座位 0: 底牌=[44,31] 净输赢=-10 亮牌=[44,31,32,35,42] 牌型=pair
座位 1: 底牌=[19,27] 净输赢=10 亮牌=[19,28,32,35,42] 牌型=pair
```

人工复算（牌编码 `card = 花色×13 + 点数 − 2`，花色 ♣♦♥♠）：
公共牌 `♥4 ♥8 ♥J ♦A ♠3`；座位 0 底牌 `♠7 ♥Q` → 最佳五张 `♠7 ♥4 ♥8 ♥J ♥Q` = 一对 4 带 Q、J、8；
座位 1 底牌 `♣8 ♦3` → `♣8 ♥8 ♥J ♦A ♠3` = 一对 8 带 A、J。两条都与服务端给出的 `pair` 与牌面一致，
输赢 ±10 也守恒。

**弃牌结束（翻牌前弃牌）：**

```
公共牌: (无)
座位 0: 净输赢=5 亮牌=[13,23] 牌型=(无)
座位 1: 净输赢=-5 亮牌=[(不亮)] 牌型=(无)
```

赢家（座位 0）亮出两张底牌 `♦2 ♦Q`，牌型为 null（不足五张，本来就没有牌型）；
弃牌者（座位 1）**一个字段都没有**，客户端据此显示「未摊牌」。这正是要的口径：
诈唬被弃牌收池时赢家亮牌，弃牌者的牌不公开。

「九个类别码映射完整且稳定」不只逐个断言，还把覆盖到的码排序后与 9 个码的全集比对——
少一个客户端就会有牌型显示不出来，这条能钉住。

`apps/server/test/settle.test.ts` 新增 2 项集成用例（真起服务端、全走 HTTP 与真实时钟）：

```

ok - 打到摊牌时每个未弃牌座位都亮出最佳五张与牌型
```

摊牌那条用「翻牌前补齐，之后三条街一路过牌」把牌局真的打到河牌（8 次动作，
不用 `advanceMatch`——它会把时钟推过整个结算窗口），再用独立算一遍的
`bestFive([...底牌, ...公共牌])` 与响应逐座位比对：既断言形状（五张、牌型码合法），
也断言内容（真的是最优五张、牌型与牌相符）。

## 七、结论

六项体验优化之后，结算弹窗补齐了用户要的「牌的组合 + 牌型 + 剩余筹码」：`npm test` 492/492、
`typecheck` 干净、穷举回归通过、42 项进程级冒烟连跑 10 次 0 失败。本次新增的 22 项测试里，
11 项是纯牌型算法单测、2 项是打到真摊牌的集成用例，其余在两端。

亮牌计算全在服务端、引擎冻结未动，字段是纯增量（老快照与老客户端都不受影响）。
第六节列出的未验证项——尤其是两端人工走查与小程序真机渲染——交付前必须自己确认。
