| 机器人反应太快 | 思考 2.5 秒起，叠加 0–2 秒抖动（2.5–4.5 秒） | `apps/server/src/config.ts:8-10`、`coordinator.scheduleTimers` |
| 每局缺 BGM | 实时合成（零音频文件），默认关、点击开启；无 Web Audio 能力时显示「音乐：不可用」 | `apps/web/static/js/music.js`、`apps/wechat/utils/music.js` |

服务端改动是纯增量的：既有字段一个没动，只多了 `actionTimeoutMs` 与 `settle` 两个只读字段
和一个 `settleAck` 命令。契约的正式修订说明见 `docs/product/contract.md` 开头的引用块。

## 三、端到端冒烟（42 项，比上次多 2 项）

`npm run smoke` 真起一个服务端进程跑完整流程。本次新增两项：
`静态页 /tutorial.html 可用`、`结算确认门可用（真人点确认，命令一路 200）`。
后者在整场对局里边打边以真人身份点确认，命令不合法会当场把冒烟打红——
等于白捡一条进程级回归。一次实测的结尾：


## 四、验证过程中发现并修复的两处测试缺陷

两处都不是产品代码的问题，是测试写法的问题；留着会让「全绿」这句话站不住。

1. **`bots.test.ts` 有一条偶发假失败，错的是断言的前提**。原断言是
   `assert.equal(view.winner, botSeat(roomId))`——「真人全弃牌时机器人必胜」。
   实测 15 次单独跑全过，但全量跑时挂了一次（`actual: 0, expected: 1`）。
   读代码后确认前提本身是错的：`packages/bot/src/strategy.ts:84` 的
   `if (equity <= price) return {type: 'fold'}` 意味着**机器人自己也会弃牌**，
   单挑时它是小盲，牌弱就让出大小盲；而发牌与机器人决策都取真实随机源，胜者由牌决定。
   改成断言「赢家必须是在本桌在座的人」，并把这句理由写进注释。
   **服务端行为没有任何改动**，改的是那句不成立的假设。

2. **`main.test.ts:106` 的 stderr 竞态**。原先 `waitForText('已启动')` 盯的是 stdout，
   而紧接着的节奏警告打印在 stderr 上（「已启动」在 `main.ts:20`，警告在 `:24`），
   机器负载高时 `proc.stderr` 还是空串就断言，偶发失败。新增 `waitForStderr`
   （与 `waitForText` 同构），改成等 stderr 上那行文字本身再断言。

修复后 `npm test` 连跑 3 次 470/470。

2. **两端界面的人工走查**：所有布局、座位定位、弹窗、音乐开关、教程页的渲染都
   只做过静态与逻辑层测试，**没有在浏览器里点过、也没有在微信开发者工具或真机里跑过**。
   微信端的浅色主题依赖 WXSS 的 CSS 变量（`page` 上的 `--accent` 等），
   这一套只在静态检查里验证过色值，**没有真机渲染截图**。
3. **90 秒与机器人节奏的真实手感**：90 秒窗口与 2.5–4.5 秒思考是注入时钟下的精确断言，
   但「玩起来是不是就不急了」「机器人是不是像人了」属于主观判断，本次没有真人试玩记录。
4. **结算确认门在多真人同桌上的真实并发**：服务端侧验证了「两人几乎同时点确认」
   （跳过版本检查）、重复确认幂等、手号对不上无副作用；但**没有两个真人真机同时点**过。
   冒烟里只有一个真人身份。
5. 上一份报告第七节的未验证项依然全部有效（微信真机登录与分享、真实 Postgres、
